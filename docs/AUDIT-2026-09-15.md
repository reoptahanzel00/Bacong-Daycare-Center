# Pre-deployment audit — 2026-09-15

Scope: `main` at `8a5a8ef` (after PR #12 ECCD Word record and PR #13 location fix), the live
Supabase project `ukzruwisvuemdjjqgoko`, and the production site
`https://bacong-daycare-center.vercel.app`. The live database was emptied of test data earlier
the same day (3 staff accounts, 0 pupils).

## Verdict

**DO NOT DEPLOY** to the school yet.

The code is in good mechanical shape. Every gate check passes (typecheck, lint, both contract
checks, build, 60/60 E2E), every API route verifies the session, and parent isolation holds at
the database. But four things would expose children's data or the barangay legally the day
real records go in:
- the privacy notice parents consent to is still a placeholder;
- it misstates who can see the data, because officials can read every child's full record;
- the service worker keeps signed-in pages in a cache that survives sign-out and is served to
  the next person offline;
- a service-role key that is public in the git history may still work, because legacy JWT keys
  are enabled.

All four are small, contained fixes: one text, one policy set, a few lines of service-worker
code, and a dashboard switch. Fixing them, plus the attendance data-loss bug (H1), would move
the verdict to **DEPLOY WITH NOTED RISKS**.

## Findings

### BLOCKER

#### B1 — Parents consent to a placeholder privacy notice
- **Where:** `src/app/privacy/page.tsx:8`, `:39`, `:44`; `src/lib/privacyNotice.ts:12`
- **What:** The published notice has no retention period and no Data Protection Officer contact.
  It says so on the page ("PLACEHOLDER — the retention period must be set…", "PLACEHOLDER —
  add the contact details of the Barangay's Data Protection Officer"). The version recorded
  against every consent is `draft-2026-08-28`.
- **How it fails:** From go-live, every parent who registers is recorded as consenting to a
  draft notice for their child's personal and sensitive information. RA 10173 requires the
  data subject to be told the retention period and how to exercise their rights.
- **Evidence:** `grep -n PLACEHOLDER src/app/privacy/page.tsx` → lines 8, 39, 44;
  `PRIVACY_NOTICE_VERSION = 'draft-2026-08-28'`.
- **Fix:** Get DPO-approved wording (retention period, DPO name/contact, and the email
  processor used for alerts), replace the placeholders, and bump `PRIVACY_NOTICE_VERSION`.
  Existing consents are then re-requested by the version check.

#### B2 — Officials can read every child's full record; the notice says they see only figures
- **Where:** `supabase/schema.sql`:
  - `:405` Sociodemographic
  - `:435` Parent Notes Staff
  - `:445` Health Logs Staff
  - `:455` ECCD Scores Staff
  - `:483` Child Backgrounds Staff
  - `:362` Pupils and `:383` Guardians (all include `'official'`)

  Also `src/app/api/pupils/route.ts:40-42` (returns `*, guardian, sociodemographic` to any
  role) and `src/app/api/eccd/report/route.ts:39` (only parents are scoped; officials get any
  child's full record).
- **What:** The notice promises: "Barangay Officials see enrolment and attendance figures for
  oversight and reporting" (`src/app/privacy/page.tsx:34`). In fact an official can read, for
  every child:
  - name, birth date and address;
  - guardian name and phone;
  - the parents' names, ages, occupations and education;
  - health logs;
  - parents' absence notes;
  - the ECCD Examiner's Notes ("family problems / economic conditions").

  This works through the API and directly through PostgREST with the public anon key.
- **How it fails:** A signed-in official calls `GET /api/eccd/report?pupil_id=<any>&format=json`
  or `GET /api/pupils`, and receives identifiable, sensitive records. Processing is broader
  than disclosed and not proportionate to "oversight and reporting".
- **Evidence:** Policy text above: `USING (public.current_user_role() IN ('worker', 'official',
  'barangay_admin'))`. The report route branches only on `session.role === 'parent'`.
- **Fix:**
  - Remove `'official'` from the SELECT-staff policies on `child_backgrounds`, `parent_notes`,
    `health_logs`, `sociodemographic_profiles` and the `eccd_*` tables.
  - Deny officials in `/api/eccd/report` and `/api/eccd/background`.
  - Have `/api/pupils` return only the columns the official dashboard renders (name,
    guardian name, status, absences).
  - Ship this as a migration plus the `schema.sql` mirror.
  - If the DPO decides officials *should* see more, change the notice to say exactly that.

#### B3 — Signed-in pages are cached by the service worker and survive sign-out
- **Where:** `public/sw.js:36-41` (caches every 200 same-origin GET that isn't `/api/` or
  `/_next/`); `src/app/page.tsx:23-25` (the root page server-renders the roster via
  `loadInitialAppData()`); `src/data/mockData.ts:323` `clearStoredData()` (clears
  `localStorage` only; Cache Storage is never cleared).
- **What:** The HTML of `/` contains the signed-in user's roster (children's names and, for
  staff, guardian details). It is written to Cache Storage on every visit. Sign out does not
  remove it. When the network fails, the worker serves it for any navigation (`caches.match`,
  falling back to `caches.match('/')`).
- **How it fails:** On a shared daycare phone, a worker signs out. The next person opens the
  app on weak or no signal. The service worker serves the cached `/`, and the previous user's
  roster renders without any session. It is also readable through DevTools → Cache Storage at
  any time.
- **Evidence:** Code as quoted. Not reproduced in a browser in this audit; see "Not verified".
- **Fix:**
  - In `sw.js`, cache only the static shell (or nothing) for navigations, and never cache
    responses for authenticated pages.
  - On sign-out, call `caches.keys()` → `caches.delete()` alongside `clearStoredData()`.
  - Bump `CACHE_NAME` so existing caches are dropped on the next activation.

#### B4 — A service-role key is public in git history while legacy JWT keys are still enabled
- **Where:** Git history (`git log --all -S service_role` → `4a4b9d5`, `a0d4949`); repository
  `reoptahanzel00/Bacong-Daycare-Center` is `PUBLIC` (`gh repo view --json visibility`);
  Supabase project API keys.
- **What:** The legacy `service_role` JWT committed in `4a4b9d5` is fetchable by anyone who
  clones the repo. It bypasses every RLS policy. Legacy JWT keys are still enabled: the legacy
  anon key authenticated a sign-in at 14:16 today, and the live Vercel build still uses it.
- **How it fails:** Anyone with the leaked key gets unrestricted read/write over every child,
  guardian and health record, unless the project's legacy JWT keys are disabled.
- **Evidence:** As above. The leaked key itself was deliberately not exercised (see "Not
  verified").
- **Fix (in progress):**
  1. Set Vercel `NEXT_PUBLIC_SUPABASE_ANON_KEY` to the publishable key and
     `SUPABASE_SERVICE_ROLE_KEY` to the secret key.
  2. Redeploy.
  3. Verify the site.
  4. Supabase → API Keys → **disable legacy JWT keys**. This order matters: disabling first
     takes the live site down.

### HIGH

#### H1 — A failed attendance save reports success and is never synced
- **Where:** `src/app/api/attendance/bulk/route.ts:48-55` (returns `success: true` with a
  warning when the upsert fails) and `:94-96` (returns `success: true` with no warning when
  the database throws); `src/contexts/DaycareContext.tsx:681` (only `!res.success` is surfaced);
  `src/components/OfflineIndicator.tsx:37` ("changes save locally and sync when you're back
  online").
- **What:** No sync mechanism exists: no queue or retry anywhere in `src/` or `public/sw.js`.
  A register that failed to reach the database lives only in `localStorage`, which is wiped
  at sign-out.
- **How it fails:** A worker on poor signal saves the morning register. The upsert fails, but
  the UI shows success. The register never reaches Supabase. The DSWD attendance figures, the
  absence alerts and the parent's view are all wrong, with no indication.
- **Evidence:** Code as quoted; `grep -rn -i "sync when\|retryQueue\|outbox" src public/sw.js`
  finds only the two messages.
- **Fix:** Return `success: false` (5xx) whenever the write did not land, and let the existing
  client warning fire. Change the offline banner to "Changes will not save until you're back
  online". Or implement a real outbox (persisted queue plus retry on `online`), not a promise
  of one. The same pattern exists in `/api/pupils` POST (`:150`) and `/api/progress` POST
  (`:123`).

#### H2 — The Supabase secret key was shared outside a secret store
- **Where:** Supabase project API keys (`sb_secret_…`, the key in `.env.local` and used by
  every server route).
- **What:** The full-access secret key was pasted into an AI chat session on 2026-09-15.
- **How it fails:** Anyone with access to that transcript has service-role access to the
  database.
- **Evidence:** Session record.
- **Fix:** In Supabase, create a new secret key, put it in `.env.local` and Vercel (never in
  chat), redeploy, then delete the old key.

### MEDIUM

#### M1 — The audit trail is written by the browser, not by the server actions
- **Where:** `src/services/auditService.ts:20`, `src/contexts/DaycareContext.tsx` `logAuditAction`
  (20 call sites); only `src/app/api/pupils/verify/route.ts` and `src/app/api/settings/route.ts`
  insert into `audit_log` server-side.
- **What:** Attendance saves, ECCD evaluations, pupil edits and archives are recorded only if
  the client chooses to POST `/api/audit-log` after the real call. Any authenticated user,
  parents included, can also append arbitrary action/target text (attributed to themselves,
  so it can't be forged as someone else).
- **How it fails:** Someone using a worker's session who calls the APIs directly (curl, a
  modified client, or a failed follow-up request) changes children's records with no audit
  entry. The "immutable RA 10173 audit trail" is incomplete by construction.
- **Fix:** Insert audit rows inside the write routes, using the verified session as
  `recordAudit(session, action, target)` in `src/lib`. Restrict `POST /api/audit-log` to
  staff, or remove it.

#### M2 — Roster data stays in `localStorage` when a session expires
- **Where:** `src/contexts/DaycareContext.tsx:544-547` persists pupils, attendance and progress;
  `clearStoredData()` is called only from the Sign out buttons (`src/components/Header.tsx:152`,
  `src/components/Sidebar.tsx:85`).
- **What:** If the session expires, the tab is closed, or the middleware redirects to `/login`,
  the cached roster (names, birth dates, addresses, guardian phones) stays on the device.
- **How it fails:** On a shared device, the next person can read the previous worker's roster
  through DevTools → Application → Local Storage.
- **Fix:** Call `clearStoredData()` when `/login` mounts and on Supabase `SIGNED_OUT`. Store
  only what offline use actually needs.

#### M3 — Staff accounts are not real people yet
- **Where:** `users` table (3 rows); `center_settings` (worker and captain names empty).
- **What:** The staff accounts use made-up `@bacong.gov.ph` addresses and demo names ("Teacher
  Teresa Cruz", "Hon. Juan Santos", "Admin Ricardo Mercado"). DSWD Form 1 signatories print
  "Not recorded".
- **How it fails:** "Forgot password" for staff sends mail to addresses nobody reads, and
  official forms carry demo names or blank signatories.
- **Fix:** Rename the accounts, set real emails, and fill Centre & Signatories. The demo
  passwords were already rotated today and verified rejected.

### LOW

#### L1 — Public-path checks match by prefix
- **Where:** `src/middleware.ts:13-18`
- **What:** `startsWith('/auth')` also matches `/author…`, and `/privacy` matches `/privacy-…`.
  No such routes exist today, so nothing is exposed, but a future page named that way would
  silently be public.
- **Fix:** Match `path === p || path.startsWith(p + '/')`.

#### L2 — Middleware passes requests through when Supabase env is missing
- **Where:** `src/middleware.ts:24-31`
- **What:** A deliberate choice for demo/E2E mode. In production, a missing env var would
  render the demo shell instead of failing.
- **Fix:** Fail closed when `NODE_ENV === 'production'`.

#### L3 — `supabase/.temp/` is untracked but not ignored
- **Where:** repo root (`git status --porcelain` → `?? supabase/.temp/`)
- **Fix:** Add `supabase/.temp/` to `.gitignore`.

#### L4 — Parent signup auto-confirms the email address
- **Where:** `src/app/api/auth/signup/route.ts:112` (`email_confirm: true`)
- **What:** There's no proof of email ownership. Enrollment still needs worker verification, so
  there's no data exposure, but a typo'd address locks the parent out of password recovery.
- **Fix:** Send a confirmation email, or verify the address during the worker's enrollment
  review.
