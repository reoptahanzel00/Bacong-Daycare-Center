# Pre-deployment audit — 2026-09-05

Barangay Bacong Daycare Center Tracker · branch `main` @ `3d4c213`

## Verdict

**DO NOT DEPLOY**

The code is in good shape — every mechanical gate passes and the application-layer
security work from previous passes holds up under inspection. What blocks the deploy is
not the code but the surrounding infrastructure: a Supabase `service_role` key for the
**live** project sits in the history of a **public** GitHub repository, two tables ship
with Row Level Security switched off in a database where the anon key is public, and the
published privacy notice is still a self-described draft with a placeholder retention
period. Any one of those is a reason to hold. Together they mean the first real child
record entered into this system would be entered into a database a stranger can read.

None of the three requires much work. B1 is a key rotation in the Supabase dashboard,
B2 is four lines of SQL, B3 is wording the barangay has to supply. This can plausibly
be a same-day deploy — just not a deploy before they are done.

## Findings

### BLOCKER

#### B1 — A live `service_role` key is published in a public GitHub repository

- **Where:** commit `3a204ad` (2026-08-11), in `src/lib/supabase/admin.ts`,
  `src/lib/supabase/client.ts` and `src/lib/supabase/server.ts`
- **What:** those three files once carried hardcoded Supabase credentials as fallbacks.
  They were removed from the working tree in `a0d4949`, but removal from a later commit
  does not remove anything from history. The blob is still fetchable, and the repository
  `github.com/reoptahanzel00/Bacong-Daycare-Center` is **public** (`"visibility":"PUBLIC"`,
  confirmed via `gh repo view`).
- **How it fails:** decoding the leaked JWT's payload gives
  `{"iss":"supabase","ref":"ukzruwisvuemdjjqgoko","role":"service_role","exp":2101940575}`.
  The project reference `ukzruwisvuemdjjqgoko` is **the same project this app points at
  today** — `NEXT_PUBLIC_SUPABASE_URL` in `.env.local` resolves to that exact ref. The
  expiry is in 2036. A `service_role` key bypasses every RLS policy in this audit, so
  anyone who clones the repo and runs `git log -p` gets unrestricted read and write over
  every pupil, guardian, health log and ECCD record in the live database.
- **Evidence:** `git show 3a204ad:src/lib/supabase/admin.ts` returns a 219-character JWT
  whose payload decodes to the claims above. The current `.env.local` key is 41
  characters beginning `sb_secret_` — a *different*, newer-format key, so the project has
  been migrated to Supabase's new API key format. That is good but not sufficient: the
  anon key in `.env.local` is still a legacy `eyJ...` JWT, which means legacy JWT keys are
  **still enabled** on the project. While they are enabled, the leaked `service_role` JWT
  is expected to still authenticate.
- **Not proven:** whether the leaked key currently returns data. The live probe against
  `ukzruwisvuemdjjqgoko.supabase.co/rest/v1/` was blocked by this environment's command
  classifier, so the "still works" step is inference from the key format, not a
  demonstration. It does not change the fix — a `service_role` key that has been public
  for weeks must be revoked whether or not it answers today.
- **Fix:**
  1. Supabase Dashboard → Project Settings → API Keys → **disable legacy JWT keys**
     (this invalidates the leaked `service_role` JWT and the current anon JWT together).
  2. Move the app's anon key to the new publishable format (`sb_publishable_...`) and
     update `NEXT_PUBLIC_SUPABASE_ANON_KEY` locally and in Vercel.
  3. Rotate `sb_secret_...` as well, on the assumption that anything derived from the
     compromised window is suspect.
  4. Decide about the history itself. Rewriting it (`git filter-repo`) or making the
     repository private closes the exposure to future readers; neither un-publishes what
     has already been cloned or indexed, which is why revocation, not rewriting, is the
     step that actually matters.

#### B2 — Two tables ship with Row Level Security disabled, and the anon key is public

- **Where:** `supabase/schema.sql:13` (`school_years`), `supabase/schema.sql:97`
  (`progress_domains`); the `ENABLE ROW LEVEL SECURITY` block runs from line 289 and
  covers 14 of the 16 tables — these two are absent
- **What:** Supabase grants the `anon` and `authenticated` roles full DML on tables in
  the `public` schema by default, and RLS is the only thing that takes it back.
  `schema.sql` contains no `GRANT` or `REVOKE` statements at all (`grep -n "GRANT\|REVOKE"`
  returns nothing), so nothing else constrains these two tables.
- **How it fails:** `NEXT_PUBLIC_SUPABASE_ANON_KEY` ships in the browser bundle by
  design — it is public. With RLS off, anyone who opens DevTools on the deployed site can
  take that key and issue `DELETE FROM progress_domains` against the REST endpoint with no
  account at all. `progress_observations.domain_id` is a foreign key into that table
  (`schema.sql:122`), so the entire ECCD progress system loses its reference data and every
  worker's evaluation screen breaks. The same applies to `school_years`, which the DSWD
  annual report keys on.
- **Fix:** add to `schema.sql` alongside the other twelve, and ship as a migration:

  ```sql
  ALTER TABLE school_years ENABLE ROW LEVEL SECURITY;
  CREATE POLICY "School Years SELECT Auth Policy" ON school_years
    FOR SELECT TO authenticated USING (true);

  ALTER TABLE progress_domains ENABLE ROW LEVEL SECURITY;
  CREATE POLICY "Progress Domains SELECT Auth Policy" ON progress_domains
    FOR SELECT TO authenticated USING (true);
  ```

  Read-only for signed-in users matches how `center_settings` and `announcements` are
  already handled (`schema.sql:371`, `:379`); writes to both tables belong to the service
  role, as they already do everywhere else.

#### B3 — The published privacy notice is a placeholder, and consent is being recorded against it

- **Where:** `src/app/privacy/page.tsx:39` and `:44`; `src/lib/privacyNotice.ts:12`
- **What:** the notice at `/privacy` states, in the text a parent actually reads,
  `'PLACEHOLDER — the retention period must be set by the Barangay and stated here before
  this notice is published.'` and, for data-subject rights,
  `'PLACEHOLDER — add the contact details of the Barangay's Data Protection Officer here.'`
  `PRIVACY_NOTICE_VERSION` is `'draft-2026-08-28'`.
- **How it fails:** `/api/auth/signup` requires `consentAccepted: true` and stores
  `privacy_consent_version` against the account. On the day this goes live, every parent
  who registers has a recorded, versioned consent — to a document that names no retention
  period and no Data Protection Officer. Under RA 10173 that is not informed consent, and
  the data subjects are children.
- **Fix:** this one is not code. The barangay's Data Protection Officer supplies the
  retention period and contact details; replace both placeholder strings, bump
  `PRIVACY_NOTICE_VERSION` to a non-draft value, and remove the draft banner at
  `page.tsx:65-71`. The versioning is already built to force re-consent when that value
  changes, so accounts created before the change will be asked again — which is the
  correct outcome.

  Credit where due: the placeholder is loud and deliberate rather than hidden, with a
  comment at `page.tsx:8` explaining exactly this risk. The mechanism worked. It now
  needs someone to act on it.

### HIGH

#### H1 — Dates are computed in UTC, so early-morning records file under the previous day

- **Where:** 14 call sites; the ones that matter are `src/views/WorkerView.tsx:79`
  (attendance register default date), `src/views/ParentView.tsx:62` (absence reporting),
  `src/app/api/health-logs/route.ts:58`, `src/app/api/eccd/route.ts:112`,
  `src/app/api/pupils/route.ts:79` and `:104`, `src/app/api/auth/signup/route.ts:181`
- **What:** every one uses `new Date().toISOString().split('T')[0]`. `toISOString()`
  converts to UTC. The Philippines is UTC+8.
- **How it fails:** a worker opens the attendance register at 07:30 on 5 September.
  The browser's `Date` is correct local time, but `toISOString()` renders it as
  `2026-09-04T23:30:00Z`, and `split('T')[0]` yields `2026-09-04`. The register defaults
  to **yesterday**, and the morning's attendance is upserted against yesterday's row —
  overwriting the real record for the 4th and leaving the 5th blank. The window is
  00:00–07:59 local, which is exactly when a morning register is taken. Server-side the
  window is the same, and Vercel functions run in UTC, so the API defaults are affected
  every day for those eight hours regardless of the caller.
- **Fix:** one helper, used everywhere:

  ```ts
  // src/lib/dates.ts
  /** Today's date in the centre's timezone (UTC+8), as YYYY-MM-DD. */
  export function todayLocalISO(): string {
    return new Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Manila' }).format(new Date());
  }
  ```

  `en-CA` formats as `YYYY-MM-DD`, so no string surgery is needed. Replace all 14 sites.
  This deserves a regression test: freeze the clock at 23:30 UTC and assert the register
  defaults to the following local day.

#### H2 — The documented production setup seeds six fictional children

- **Where:** `supabase/seed.sql:34` (pupils), `:44` (guardians), `:54` (announcements),
  and a demo attendance block from `:60`
- **What:** the inserts are unconditional. There is no environment guard, no
  `WHERE current_setting(...)`, nothing that distinguishes staging from production.
- **How it fails:** `DEPLOYMENT.md` § "Supabase Database Setup" instructs, as step 2 of
  the production setup, to run `seed.sql` in the SQL Editor. Following the documentation
  as written puts Mateo Santos, Sophia Reyes, Gabriel Dela Cruz, Althea Mendoza, Lucas
  Bautista and Samantha Villanueva into the live roster, with guardian names and phone
  numbers. They then flow into the enrolment counts on DSWD Form 1 — a document the
  barangay captain signs and submits to a national agency. A signed government return
  overstating attendance by six children is a materially worse problem than a messy
  demo database.
- **Fix:** split the file. Keep sections 1 and 2 (school year, `progress_domains` — real
  reference data the app needs) as `seed.sql`; move sections 3 onward to
  `seed.demo.sql`. Then correct the DEPLOYMENT.md step so it names `seed.sql` for
  production and `seed.demo.sql` for staging and UAT only.

#### H3 — The Vercel CLI is not authorised for the target account, so production config cannot be verified

- **Where:** `.vercel/project.json`
- **What:** the project file pins `projectName: bacong-daycare-center`,
  `orgId: team_T7W0cYNn7ri6982TISzlm7lU`. The CLI session on this machine cannot reach it.
- **Evidence:**

  ```
  npx vercel whoami              → Error: Not authorized
  npx vercel teams ls            → kasi-guru / KasiGuru        (the only team visible)
  npx vercel env ls production   → Error: Could not retrieve Project Settings
  ```

  The one team this session can see is not the team the project belongs to.
- **How it fails:** two consequences. The deploy cannot run at all from here. And more
  importantly, the audit cannot confirm what production is configured with — in
  particular whether `KV_REST_API_URL` / `KV_REST_API_TOKEN` are set. If they are not,
  `src/lib/rateLimit.ts:88` silently falls back to a per-instance counter, and the
  sign-in limit of 10 attempts per 15 minutes becomes 10 *per serverless instance*
  rather than 10 per attacker — which, on the sign-in route of a system holding
  children's records, is close to no limit at all.
- **Fix:** `npx vercel login` with the account that owns `bacong-daycare-center`, then
  re-run `npx vercel env ls production` and confirm the Upstash pair is present. Per the
  standing rule for this project, deploy only to that account — never a personal one.

### MEDIUM

#### M1 — The service-role client has no `server-only` guard

- **Where:** `src/lib/supabase/admin.ts:1`
- **What:** `server-only` is a project dependency and is used at
  `src/lib/initialData.ts:1`, but not here. Nothing currently imports `admin.ts` from a
  client component — every one of its 20 importers is an API route or `src/lib/notify.ts`,
  and none carries `'use client'` — so there is no live exposure.
- **How it fails:** the guard is what makes a future mistake fail at build time rather
  than shipping the service-role key into a browser bundle. Its absence is the difference
  between "we checked, it's fine today" and "it cannot happen".
- **Fix:** add `import 'server-only';` as the first line.

#### M2 — No dialog semantics or focus management in any modal

- **Where:** all ten `src/components/*Modal.tsx` files plus
  `src/components/NotificationDrawer.tsx`
- **What:** none has `role="dialog"`, `aria-modal="true"`, an Escape handler, a focus
  trap, or focus restoration on close (`grep -c 'Escape'` and `grep -c 'role="dialog"'`
  return 0 for all eleven).
- **How it fails:** a keyboard user who opens the pupil form tabs straight out of it into
  the page behind, with no way back and no indication the dialog is still open. A screen
  reader user is never told a dialog opened at all. This is the one substantive gap left
  in an accessibility story that is otherwise well handled.
- **Fix:** one shared `useModalA11y(isOpen, onClose)` hook (`src/hooks/useModalA11y.ts`)
  returning props to spread onto the overlay. It sets `role="dialog"` and
  `aria-modal="true"`, names the dialog from its own `<h3>` via `aria-labelledby`, moves
  focus into it on open, wraps Tab at both ends, closes on Escape, and returns focus to
  the opener on close. Shared rather than written eleven times because eleven hand-rolled
  copies will not stay in sync, and a modal added later inherits it.

  `NotificationDrawer` is deliberately **excluded**. It is a popover anchored to the bell
  icon, not a modal — it does not cover the page and does not make the rest of it inert,
  so `aria-modal="true"` would be a false claim to a screen reader. It received the
  `aria-label` fix from M3 only.

#### M3 — Fourteen icon-only buttons have no accessible name

- **Where:** every modal's close control, plus `src/components/MobileNav.tsx`,
  `src/components/Toast.tsx`, `src/components/NotificationDrawer.tsx` and the
  verification dialog in `src/views/WorkerView.tsx`
- **What:** each renders a bare `<X>` icon with no `aria-label` and no text, so a screen
  reader announces only "button" — the user is told there is a control but not that it
  closes the dialog they are trapped in. The convention exists elsewhere in the codebase
  (`src/components/Header.tsx:89`, `:113`), so these are omissions rather than a missing
  pattern.
- **Correction to an earlier count:** the first sweep of this audit reported *two*. That
  came from a single-line grep, and all but two of these buttons are written across
  several lines, so the pattern matched almost none of them. The real figure is fourteen.
  A multi-line sweep found the rest.
- **Fix:** `aria-label` on all fourteen — "Close" for the dialog controls, "Close
  navigation" for the mobile drawer, "Dismiss notification" for the toast. Two buttons in
  `WorkerView` that contain an `<X>` icon *and* visible text ("Reject", "Confirm
  Rejection") were deliberately left alone: they already have accessible names.

## Green — confirmed working

These were checked and hold. Listed so a later reader knows they were proven, not merely
unmentioned.

- **Gate 0 in full.** Type check, lint, the UUID contract check across 32 routes, the
  production build, and 46 Playwright tests — all pass on this machine.
- **Session verification is universal.** Every route under `src/app/api/**` calls
  `getServerSession()` except `/api/health` (returns only `status` and a timestamp — no
  environment or version disclosure), `/api/auth/login`, `/api/auth/session` and
  `/api/auth/signup`, which are the sign-in surface by definition and are rate limited.
- **Auth fails closed.** `src/lib/auth.ts:57` returns an unauthenticated session on any
  error, missing profile, unknown role, or disabled account. Roles are read from the
  `users` table, never from user-editable `user_metadata`.
- **No privilege self-assignment.** `/api/auth/signup` rejects a requested non-parent role
  before body validation, so an escalation attempt is refused rather than reported as a
  validation error.
- **The service-role client is server-side only in practice.** All 20 importers are API
  routes or `src/lib/notify.ts`; none is a client component. (The compile-time guard is
  M1.)
- **The rate limiter degrades correctly.** `src/lib/rateLimit.ts` accepts both the
  Marketplace (`KV_REST_API_*`) and direct-Upstash (`UPSTASH_REDIS_REST_*`) variable
  pairs, and on a Redis outage falls back to the in-process bucket rather than failing
  open (no limit) or closed (nobody can sign in).
- **Parent isolation is correctly expressed** on all twelve PII-bearing tables — pupils,
  attendance, health logs, ECCD scores, child backgrounds, progress observations, parent
  notes and sociodemographic profiles all scope to
  `pupil_id IN (SELECT pupil_id FROM guardians WHERE user_id = auth.uid())`. Officials
  are deliberately excluded from individual progress notes (`schema.sql:447`). Policies
  use the `current_user_role()` SECURITY DEFINER helper, avoiding recursive evaluation
  on `users`.
- **The audit log is genuinely immutable from the client.** No INSERT policy exists;
  writes go through `/api/audit-log` on the service role with the actor derived from the
  verified session, so entries cannot be forged or misattributed.
- **No PII reaches the logs.** `/api/client-error` records role, path, message and
  component stack — never identity (`route.ts:44`). No `console.*` call anywhere
  interpolates a record object.
- **Attendance writes cannot duplicate.** `upsert` with `onConflict: 'pupil_id,date'`
  makes a resubmitted register idempotent, and guardian alerts are deferred with
  `after()` so delivery never blocks the worker's save.
- **The enrolment verification bypass stays closed.** `resolveEnrollmentStatus()`
  (`src/lib/enrollment.ts:23`) pins `pending` and `rejected` records so a demographic
  edit cannot double as an approval, and `tests/enrollment*.spec.ts` cover it.
- **Schema and migration are in step.** All three deltas in
  `20260828_01_deployment_readiness.sql` are present in `schema.sql`: the windowed
  absence trigger (`:508`, `ROWS UNBOUNDED PRECEDING`), `center_settings` (`:26`), and
  the consent columns (`:45-46`).
- **Accessibility fundamentals hold.** Focus rings are enforced globally with
  `!important` so no Tailwind utility can remove them (`globals.css:114`), 44px minimum
  tap targets are applied under `@media (pointer: coarse)` (`:141`), and the palette is
  tokenised with contrast ratios documented at the definitions (`--primary: #247571`,
  5.44:1 on white).
- **Security headers are correct.** CSP, `frame-ancestors 'none'`, Permissions-Policy,
  HSTS gated to production, and `unsafe-eval` correctly dev-only (`next.config.mjs`).
  `/sw.js` and `/manifest.json` are `no-store`.
- **No secrets in the current tree.** No `NEXT_PUBLIC_*` variable carries a secret, no
  JWT literal remains in `src/`, `scripts/` or `supabase/`, `.gitignore` denies `.env*`
  by default with only `.env.example` allowed back, and `.env.example` is the only env
  file tracked. (The problem is history, not the tree — B1.)
